# Graph-Build Harness — Build Spec for Claude Code

You are setting up a small, personal-use harness that lets me build apps as a **graph of agents** inside Claude Code. Read this whole file before creating anything, then build it in the order under "Build Order." Ask me only if something here is genuinely ambiguous.

## Goal

A reusable set of agents, skills, one command, and one script that:

1. Turns an idea into a design doc (with my approval),
2. Turns the design into a dependency graph of build nodes (`plan/manifest.json`),
3. Runs each node with a **builder** agent and checks it with a separate **verifier** agent that cannot edit code,
4. Fans out independent nodes in parallel using git worktrees,
5. Retries failed nodes (max 3) with the verifier's notes attached,
6. Stops and tells me when something is blocked or when everything is verified.

Design principles: prompts for judgment, scripts for control flow, tool restrictions for anything that must be true regardless of what the model decides. Producer and verifier are never the same agent. The orchestrator routes; it never builds or grades.

This is the personal version. **Do not add** hooks, budgets, schema validation, plugin packaging, a GUI, or a code-based scheduler. Keep every file short.

## Directory Layout

Create this in the **current repo** (project-scoped), not globally:

```
.claude/
  commands/build-app.md
  agents/planner.md
  agents/builder.md
  agents/verifier.md
  skills/manifest/SKILL.md
  skills/stack/SKILL.md
run/
  next.py
  state/            # generated, one JSON per node; add .gitkeep
plan/
  design.md         # generated by brainstorm
  manifest.json     # generated by planner
```

Add `run/state/*.json` and `.worktrees/` to `.gitignore`.

## State Model

Each node writes `run/state/<node-id>.json`:

```json
{
  "id": "api-ing",
  "status": "pending | building | verifying | verified | failed | blocked",
  "attempts": 1,
  "worktree": ".worktrees/api-ing",
  "verdict": "pass | fail | null",
  "notes": "verifier's reasons on fail; empty on pass",
  "updated": "ISO-8601"
}
```

Rules:
- A node is **ready** when `status` is `pending` or `failed`, `attempts < 3`, and every dep has `status == verified`.
- A node becomes **blocked** when `attempts == 3` and `verdict == fail`.
- `next.py` is the only thing that decides readiness. Agents write state; they never decide ordering.

## Manifest Format (`plan/manifest.json`)

```json
{
  "app": "recipe-tracker",
  "nodes": [
    {
      "id": "schema",
      "desc": "DB schema: recipes, ingredients, recipe_ingredients, units",
      "deps": [],
      "accept": [
        "migrations apply cleanly on empty DB",
        "recipe_ingredients enforces FK to both parents"
      ]
    },
    {
      "id": "api-ing",
      "desc": "Ingredient CRUD API + unit normalization",
      "deps": ["schema"],
      "accept": [
        "POST/GET/PUT/DELETE ingredient round-trips",
        "'tbsp' and 'tablespoon' normalize to the same unit"
      ]
    }
  ]
}
```

- `id`: kebab-case, unique, also used as worktree/branch name.
- `deps`: list of ids. No cycles.
- `accept`: 2–5 concrete, testable criteria. The verifier checks exactly these.

## Files to Create

### `.claude/skills/manifest/SKILL.md`

Frontmatter: `name: manifest`, description: "How to write plan/manifest.json for the graph-build harness. Use when decomposing a design into build nodes."

Body: the manifest format above, the rules, and guidance:
- Prefer 4–8 nodes for a small app. Split by *interface boundary* (schema / API / UI / cross-cutting feature), not by file.
- Every node must be buildable and testable in isolation given only its deps.
- Acceptance criteria must be checkable by running something, not by reading code.
- Always include a final `e2e` node that depends on all leaf nodes.

### `.claude/skills/stack/SKILL.md`

Frontmatter: `name: stack`, description: "Project stack conventions for the graph-build harness. Use when implementing any node."

Body: **leave this as a template with a TODO** — I'll fill in language, framework, test runner, and lint commands per project. Include placeholder sections: Language & runtime, Framework, Test command, Lint/format command, Directory conventions, Things never to do.

### `.claude/agents/planner.md`

Frontmatter: `name: planner`, description: "Turns plan/design.md into plan/manifest.json." Tools: `Read, Write, Glob, Grep`.

System prompt (short): You read `plan/design.md` and produce `plan/manifest.json` using the `manifest` skill. You do not write code. Output only the manifest file and a 3-line summary of the node count and dependency depth.

### `.claude/agents/builder.md`

Frontmatter: `name: builder`, description: "Implements one manifest node in its own worktree, tests first." Tools: `Read, Write, Edit, Bash, Glob, Grep`.

System prompt (short):
- You are given a node id. Read its entry in `plan/manifest.json` and `run/state/<id>.json`. If `notes` is non-empty, those are the verifier's reasons your last attempt failed — address them explicitly.
- Work **only** inside the worktree path in state. Never touch files outside it.
- Follow the `stack` skill.
- Write failing tests for each acceptance criterion first, then implement until they pass.
- Do not modify tests written by a previous attempt unless they are wrong against the acceptance criteria; if you do, say why.
- When done, set state `status: verifying` and write a short summary of what changed into `run/state/<id>.summary.md`.

### `.claude/agents/verifier.md`

Frontmatter: `name: verifier`, description: "Independently verifies a built node against its acceptance criteria." Tools: `Read, Bash, Glob, Grep` — **no Write, no Edit**.

System prompt (short):
- You are given a node id. Read its manifest entry, its state, and its worktree.
- Run the project's test command from the `stack` skill inside the worktree.
- For each acceptance criterion, state PASS or FAIL with one line of evidence (a test name, a command output).
- Verdict is `pass` only if every criterion passes and the suite is green.
- Write your verdict by printing a single JSON object to stdout: `{"verdict": "pass|fail", "notes": "..."}` — the orchestrator will record it. You cannot and must not edit any file.
- Be specific in `notes` on fail: the builder will read it as its instructions for the next attempt.

### `run/next.py`

Python 3, stdlib only, ~40–60 lines. Behavior:

```
python run/next.py            → prints ready node ids, one per line
                              → prints "DONE" if all nodes verified
                              → prints "BLOCKED <id>" for any blocked node (and exits 1)
python run/next.py init       → creates run/state/<id>.json (status pending, attempts 0) for every manifest node; idempotent
python run/next.py status     → prints a table: id | status | attempts | verdict
python run/next.py record <id> <pass|fail> "<notes>"
                              → updates state: on pass → verified; on fail → attempts+1, failed (or blocked at 3), stores notes
python run/next.py start <id> → sets status building, creates worktree path in state
```

Detect dependency cycles in `init` and exit with an error. Keep it boring and readable.

### `.claude/commands/build-app.md`

This is the orchestrator. Frontmatter description: "Build an app as a graph of builder/verifier nodes."

Prompt body, roughly:

> You are the **orchestrator**. You route work; you never write application code and never judge whether code is correct. Argument: `$ARGUMENTS` (the app idea, or "resume").
>
> **Phase 1 — Brainstorm** (skip if `plan/design.md` exists or argument is "resume"): Interview me about the idea — users, platform, core entities, must-have vs. later, anything ambiguous. Keep asking until you could write the design without guessing. Write `plan/design.md` (scope, entities, key flows, non-goals). Then **stop and ask me to approve.** Do nothing else until I say approved.
>
> **Phase 2 — Plan** (skip if `plan/manifest.json` exists): Launch the `planner` agent. When it finishes, show me the node list and dependency graph as indented text. Ask if I want changes. Then run `python run/next.py init`.
>
> **Phase 3 — Loop**:
> 1. Run `python run/next.py`.
> 2. If output is `DONE`, go to Phase 4.
> 3. If output starts with `BLOCKED`, print `python run/next.py status`, summarize the blocked node's notes, and stop.
> 4. For every id printed: run `python run/next.py start <id>`, create a git worktree at `.worktrees/<id>` on branch `node/<id>` from main, then launch the `builder` agent for that id. Launch all ready builders **in parallel**.
> 5. For each builder that finishes, launch the `verifier` agent for that id. Parse its JSON output and run `python run/next.py record <id> <verdict> "<notes>"`.
> 6. Print `python run/next.py status`. Return to step 1.
>
> **Phase 4 — Done**: Print the final status table and list the worktree branches in dependency order so I can merge them. Do not merge.
>
> Never edit files under the worktrees yourself. If an agent fails to produce output, record it as `fail` with the note "agent produced no output" and continue.

## Build Order

1. Create the directory layout and `.gitignore` entries.
2. Write `run/next.py`. Test it against a **hand-written** `plan/manifest.json` with two nodes (`schema` → `api-ing`): run `init`, `status`, then `next.py` should print `schema`; `record schema pass ""`; `next.py` should print `api-ing`; `record api-ing fail "x"` three times; `next.py` should print `BLOCKED api-ing`. Fix until this sequence works.
3. Write the two skills.
4. Write the three agents.
5. Write `build-app.md`.
6. Delete the test manifest and state files. Leave `plan/` and `run/state/` empty (with `.gitkeep`).
7. Print a short summary of every file created and the exact command to run first: `/build-app "recipe and ingredient tracker"`.

## First Real Run (for me, not you)

I'll fill in `.claude/skills/stack/SKILL.md`, then run `/build-app` with a tiny hand-edited manifest first to debug the harness separately from the planner. Only after the loop runs cleanly on two nodes will I let the planner generate a real manifest.

## Non-Goals

No hooks, no token budgets, no schema validation, no plugin packaging, no GUI, no headless/CI mode, no integrator agent (I merge). If you find yourself adding any of these, stop.
