# Graph-Build Harness — Design

## Goal

A reusable, personal-use set of agents, skills, one command, and one script — built inside this repo's `.claude/` directory — that lets apps be built as a graph of Claude Code agents:

1. Turn an idea into a design doc (with the user's approval).
2. Turn the design into a dependency graph of build nodes (`plan/manifest.json`).
3. Run each node with a **builder** agent and check it with a separate **verifier** agent that cannot edit code.
4. Fan out independent nodes in parallel using git worktrees.
5. Retry failed nodes (max 3) with the verifier's notes attached.
6. Stop and report when something is blocked, or when everything is verified.

## Design principles

- Prompts for judgment, scripts for control flow, tool restrictions for anything that must be true regardless of what the model decides — and where a tool restriction alone can't actually guarantee that (see the verifier below), a script-enforced structural check backs it up.
- Producer and verifier are never the same agent.
- The orchestrator routes; it never builds or grades.
- Keep every file short. No hooks, token budgets, schema validation, plugin packaging, GUI, headless/CI mode, or auto-merge agent (the user merges manually). If a change seems to call for one of these, stop and flag it rather than add it.

## Directory layout

Project-scoped, in this repo:

```
.claude/
  commands/build-app.md
  agents/planner.md
  agents/builder.md
  agents/verifier.md
  skills/manifest/SKILL.md
  skills/stack/SKILL.md
run/
  next.py
  state/            # generated, one JSON per node; .gitkeep
plan/
  design.md         # generated by the brainstorm phase
  manifest.json     # generated by the planner
```

`.gitignore`: `run/state/*.json`, `.worktrees/`.

Git is initialized locally (`main` branch, one empty-ish initial commit) as part of setting this up, since worktrees require a repo to branch from.

## State model

Each node writes `run/state/<node-id>.json`:

```json
{
  "id": "api-ing",
  "status": "pending | building | verifying | verified | failed | blocked",
  "attempts": 1,
  "worktree": ".worktrees/api-ing",
  "verdict": "pass | fail | null",
  "notes": "verifier's reasons on fail; empty on pass",
  "pre_verify_head": "git commit sha, set when verification starts",
  "updated": "ISO-8601"
}
```

Rules:
- A node is **ready** when `status` is `pending` or `failed`, `attempts < 3`, and every dep has `status == verified`.
- A node becomes **blocked** when `attempts == 3` and `verdict == fail`.
- `next.py` is the only thing that decides readiness and applies the mutation guard (below). Agents write state (indirectly, via `next.py` commands, or directly for fields agents own); they never decide ordering.
- The builder must leave its worktree with all work **committed** (`git add -A && git commit`) before verification starts. This is what makes the mutation guard cheap and reliable.

## Manifest format (`plan/manifest.json`)

```json
{
  "app": "recipe-tracker",
  "nodes": [
    {
      "id": "schema",
      "desc": "DB schema: recipes, ingredients, recipe_ingredients, units",
      "deps": [],
      "accept": [
        "migrations apply cleanly on empty DB",
        "recipe_ingredients enforces FK to both parents"
      ]
    },
    {
      "id": "api-ing",
      "desc": "Ingredient CRUD API + unit normalization",
      "deps": ["schema"],
      "accept": [
        "POST/GET/PUT/DELETE ingredient round-trips",
        "'tbsp' and 'tablespoon' normalize to the same unit"
      ]
    }
  ]
}
```

- `id`: kebab-case, unique, also used as worktree/branch name.
- `deps`: list of ids. No cycles.
- `accept`: 2–5 concrete, testable criteria. The verifier checks exactly these. No schema validation on this file (non-goal) — correctness rests on the planner's judgment plus the `manifest` skill's guidance.

## The verifier mutation guard

**Problem**: the verifier is given `Bash` (to run tests) but no `Write`/`Edit`, intended to make "verifier can't edit code" a tool-level guarantee. It isn't one — `Bash` alone (`echo`, `sed -i`, committing) can still mutate files. The real enforcement point has to be a script-level check, not the tool grant.

**Fix**: `next.py` snapshots the worktree's git HEAD right before verification starts, and re-checks it when the verdict is recorded:

- `next.py begin-verify <id>` — sets `status: verifying`, records `pre_verify_head` = current HEAD sha of the node's worktree. **Refuses** if the worktree has uncommitted tracked-file changes (a builder bug — it forgot to commit — not a verifier problem, and it would otherwise make the guard meaningless since there'd be no clean baseline to diff against).
- `next.py record <id> <verdict> <notes>` — before storing anything, re-checks the worktree: if HEAD has moved, or `git status --porcelain --untracked-files=no` is non-empty (i.e. any *tracked* file changed), the guard fires: verdict is forced to `fail` and notes become `"structural guard: verifier modified tracked files"`, discarding whatever verdict/notes were actually passed in. Otherwise the given verdict/notes are recorded normally.

Untracked files are deliberately excluded from the check — test caches, coverage output, etc. produced by simply *running* the test suite during verification would otherwise cause false positives. This means a verifier could still create/modify a genuinely new untracked file without detection; that's an accepted gap for a personal, trust-based harness, not a claimed guarantee.

If `begin-verify` refused (builder left the worktree dirty), no `pre_verify_head` is set for that attempt and no verifier ever ran; the orchestrator calls `record <id> fail "builder left uncommitted changes"` directly. `record` skips the guard check whenever `pre_verify_head` is unset for the current attempt — there's nothing to diff against, and the fail is already for an unrelated reason.

Who calls `begin-verify`: the **orchestrator**, immediately after a builder agent call returns and before it launches the verifier — not the builder itself. This keeps the security-relevant checkpoint under script/orchestrator control rather than resting on the builder remembering to flip a flag correctly.

## Files to create

### `.claude/skills/manifest/SKILL.md`

Frontmatter: `name: manifest`, description: "How to write plan/manifest.json for the graph-build harness. Use when decomposing a design into build nodes."

Body: the manifest format above, its rules, and guidance:
- Prefer 4–8 nodes for a small app. Split by *interface boundary* (schema / API / UI / cross-cutting feature), not by file.
- Every node must be buildable and testable in isolation given only its deps.
- Acceptance criteria must be checkable by running something, not by reading code.
- Always include a final `e2e` node that depends on all leaf nodes.

### `.claude/skills/stack/SKILL.md`

Frontmatter: `name: stack`, description: "Project stack conventions for the graph-build harness. Use when implementing any node."

Body: left as a template with a TODO — the user fills in language, framework, test runner, and lint commands per project. Placeholder sections: Language & runtime, Framework, Test command, Lint/format command, Directory conventions, Things never to do.

### `.claude/agents/planner.md`

Frontmatter: `name: planner`, description: "Turns plan/design.md into plan/manifest.json." Tools: `Read, Write, Glob, Grep`.

System prompt: reads `plan/design.md`, produces `plan/manifest.json` using the `manifest` skill. Does not write code. Outputs only the manifest file and a 3-line summary (node count, dependency depth).

### `.claude/agents/builder.md`

Frontmatter: `name: builder`, description: "Implements one manifest node in its own worktree, tests first." Tools: `Read, Write, Edit, Bash, Glob, Grep`.

System prompt:
- Given a node id: read its entry in `plan/manifest.json` and `run/state/<id>.json`. If `notes` is non-empty, those are the verifier's reasons the last attempt failed — address them explicitly.
- Work only inside the worktree path in state. Never touch files outside it.
- Follow the `stack` skill.
- Write failing tests for each acceptance criterion first, then implement until they pass.
- Do not modify tests written by a previous attempt unless they're wrong against the acceptance criteria; if so, say why.
- When done: `git add -A && git commit` inside the worktree, and write a short summary of what changed into `run/state/<id>.summary.md`. Do not touch `status` — the orchestrator advances it via `next.py begin-verify`.

### `.claude/agents/verifier.md`

Frontmatter: `name: verifier`, description: "Independently verifies a built node against its acceptance criteria." Tools: `Read, Bash, Glob, Grep` — no Write, no Edit.

System prompt:
- Given a node id: read its manifest entry, its state, and its worktree.
- Run the project's test command from the `stack` skill inside the worktree.
- For each acceptance criterion, state PASS or FAIL with one line of evidence (a test name, a command output).
- Verdict is `pass` only if every criterion passes and the suite is green.
- Print a single JSON object to stdout: `{"verdict": "pass|fail", "notes": "..."}` — the orchestrator records it.
- Be specific in `notes` on fail — the builder reads it as its instructions for the next attempt.
- Note: any file change you make will be detected and will override your verdict to fail — don't attempt one, even though `Bash` is technically capable of it.

### `run/next.py`

Python 3, stdlib only, ~40–70 lines. Behavior:

```
next.py                        → prints ready node ids, one per line
                                  prints "DONE" if all nodes verified
                                  prints "BLOCKED <id>" for any blocked node (exit 1)
next.py init                   → creates run/state/<id>.json (status pending, attempts 0) for
                                  every manifest node; idempotent; detects dependency cycles
                                  and exits with an error
next.py status                 → prints a table: id | status | attempts | verdict
next.py start <id>              → sets status building, creates worktree path in state
next.py begin-verify <id>       → sets status verifying; records pre_verify_head = current
                                  HEAD sha of the node's worktree; refuses (non-zero exit) if
                                  the worktree has uncommitted tracked-file changes
next.py record <id> <pass|fail> "<notes>"
                                → re-checks the worktree against pre_verify_head (HEAD sha +
                                  tracked-file dirtiness); if it has moved, overrides verdict
                                  to fail with a guard note. Otherwise: on pass → verified;
                                  on fail → attempts+1, failed (or blocked at 3), notes stored.
```

Keep it boring and readable.

### `.claude/commands/build-app.md`

The orchestrator. Frontmatter description: "Build an app as a graph of builder/verifier nodes."

Prompt body, roughly:

> You are the **orchestrator**. You route work; you never write application code and never judge whether code is correct. Argument: `$ARGUMENTS` (the app idea, or "resume").
>
> **Phase 1 — Brainstorm** (skip if `plan/design.md` exists or argument is "resume"): Interview the user about the idea — users, platform, core entities, must-have vs. later, anything ambiguous. Keep asking until you could write the design without guessing. Write `plan/design.md` (scope, entities, key flows, non-goals). Then **stop and ask for approval.** Do nothing else until approved.
>
> **Phase 2 — Plan** (skip if `plan/manifest.json` exists): Launch the `planner` agent. When it finishes, show the node list and dependency graph as indented text. Ask if changes are wanted. Then run `python run/next.py init`.
>
> **Phase 3 — Loop**:
> 1. Run `python run/next.py`.
> 2. If output is `DONE`, go to Phase 4.
> 3. If output starts with `BLOCKED`, print `python run/next.py status`, summarize the blocked node's notes, and stop.
> 4. For every ready id: run `python run/next.py start <id>`, create a git worktree at `.worktrees/<id>` on branch `node/<id>` from `main`, then launch the `builder` agent for that id. Launch all ready builders **in parallel**.
> 5. For each builder that finishes: run `python run/next.py begin-verify <id>`. If it refuses (worktree not clean), record that node `fail` with note `"builder left uncommitted changes"` and skip the verifier this attempt. Otherwise launch the `verifier` agent for that id.
> 6. For each verifier that finishes: parse its JSON output and run `python run/next.py record <id> <verdict> "<notes>"`.
> 7. Print `python run/next.py status`. Return to step 1.
>
> **Phase 4 — Done**: Print the final status table and list the worktree branches in dependency order for merging. Do not merge.
>
> Never edit files under the worktrees directly. If an agent produces no output, record it as `fail` with the note "agent produced no output" and continue.

## Build order

1. `git init` (`main` branch, initial commit), directory layout, `.gitignore` entries.
2. Write `run/next.py`, including `begin-verify` and the guard in `record`. Hand-test against a hand-written `plan/manifest.json` with two nodes (`schema` → `api-ing`), including a case where a fake "verifier" mutates a tracked file between `begin-verify` and `record` to confirm the guard actually fires.
3. Write the two skills.
4. Write the three agents.
5. Write `build-app.md`.
6. Delete the test manifest and state files. Leave `plan/` and `run/state/` empty (with `.gitkeep`).
7. Print a short summary of every file created and the exact command to run first: `/build-app "recipe and ingredient tracker"`.

## First real run (user, not the agent building this)

The user fills in `.claude/skills/stack/SKILL.md`, then runs `/build-app` with a tiny hand-edited manifest first to debug the harness separately from the planner. Only after the loop runs cleanly on two nodes does the planner get to generate a real manifest.

## Non-goals

No hooks, no token budgets, no schema validation, no plugin packaging, no GUI, no headless/CI mode, no integrator agent (the user merges). If any of these seem necessary while implementing, stop and flag it rather than add it.
